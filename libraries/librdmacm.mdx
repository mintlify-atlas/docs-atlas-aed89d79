---
title: "librdmacm"
description: "RDMA connection management library"
---

librdmacm provides a connection-oriented RDMA communication interface using standard IP addressing. It allows applications to establish RDMA connections without needing to know the underlying RDMA fabric details, mapping IP addresses and port numbers to RDMA devices and paths automatically.

The library uses a single character device file regardless of the number of adapters or ports present in the system.

## Device file

librdmacm requires the device node `/dev/infiniband/rdma_cm`. To create it automatically with udev, add a rule such as:

```text udev rule
KERNEL="rdma_cm", NAME="infiniband/%k", MODE="0666"
```

To create it manually:

```bash
mknod /dev/infiniband/rdma_cm c 231 255
```

## Common issues

<AccordionGroup>
  <Accordion title="Multiple interfaces and incorrect ARP responses">
    librdmacm supports multiple network interfaces, but Linux may respond to ARP requests on a different interface than the one targeted in the ARP request. This causes the RDMA stack to map the remote IP address to the wrong RDMA device.

    To fix this, instruct the kernel to only send ARP replies on the interface that received the ARP request:

    ```bash
    sysctl -w net.ipv4.conf.all.arp_ignore=2
    ```

    Without this setting, connections over specific interfaces may be established on the wrong RDMA device.
  </Accordion>
  <Accordion title="Loopback connections timing out">
    librdmacm relies on ARP to resolve IP addresses to RDMA addresses. For loopback connections between different ports on the same system, ARP must be enabled for local resolution:

    ```bash
    sysctl net.ipv4.conf.all.accept_local=1
    ```

    Without this, loopback connections may time out during address resolution.
  </Accordion>
</AccordionGroup>

## API overview

librdmacm uses an `rdma_cm_id` as the central object, analogous to a socket. Events are reported asynchronously through an `rdma_event_channel`, which maps to a file descriptor.

| Function | Description |
|---|---|
| `rdma_create_event_channel` | Opens a channel for reporting communication events. Each channel maps to a file descriptor. |
| `rdma_create_id` | Allocates a communication identifier (`rdma_cm_id`) associated with an event channel and port space. |
| `rdma_create_ep` | Allocates an identifier and optionally a QP in one call using address info from `rdma_getaddrinfo`. |
| `rdma_bind_addr` | Binds an identifier to a local source address, optionally restricting it to a specific RDMA device. |
| `rdma_resolve_addr` | Resolves a destination IP address to an RDMA address and binds the identifier to a local device. |
| `rdma_resolve_route` | Resolves the fabric route to the destination after `rdma_resolve_addr` completes. |
| `rdma_connect` | Initiates an active connection request to a remote destination. |
| `rdma_listen` | Begins listening for incoming connection requests on a bound identifier. |
| `rdma_get_request` | Retrieves the next pending connection request from a listening identifier (synchronous). |
| `rdma_accept` | Accepts an incoming connection request on the new identifier provided by the connection request event. |
| `rdma_reject` | Rejects an incoming connection request, optionally including private data. |
| `rdma_disconnect` | Disconnects a connection and transitions the associated QP to the error state. |
| `rdma_get_cm_event` | Retrieves the next pending event from an event channel (blocking by default). |
| `rdma_ack_cm_event` | Releases an event returned by `rdma_get_cm_event`. Every event must be acknowledged. |
| `rdma_getaddrinfo` | Resolves a hostname and service to `rdma_addrinfo` structures for use with `rdma_create_ep`. |

## Client and server patterns

<Tabs>
  <Tab title="Server (passive side)">
    The server uses `rdma_create_ep` with `RAI_PASSIVE` to bind and listen. After a connection request arrives, `rdma_get_request` returns a new endpoint for the incoming connection.

    ```c
    #include <rdma/rdma_cma.h>

    struct rdma_addrinfo hints = {
        .ai_flags    = RAI_PASSIVE,
        .ai_port_space = RDMA_PS_TCP,
    };
    struct rdma_addrinfo *res;
    struct rdma_cm_id *listen_id, *conn_id;
    struct ibv_qp_init_attr qp_init_attr = {
        .cap = {
            .max_send_wr  = 64,
            .max_recv_wr  = 64,
            .max_send_sge = 1,
            .max_recv_sge = 1,
        },
        .qp_type = IBV_QPT_RC,
    };

    /* Resolve address and create listening endpoint */
    rdma_getaddrinfo(NULL, "7471", &hints, &res);
    rdma_create_ep(&listen_id, res, NULL, &qp_init_attr);
    rdma_freeaddrinfo(res);

    /* Start listening */
    rdma_listen(listen_id, 0);

    /* Wait for a connection request */
    rdma_get_request(listen_id, &conn_id);

    /* Accept the connection */
    rdma_accept(conn_id, NULL);

    /*
     * Post receives and sends on conn_id->qp,
     * then disconnect when done.
     */
    rdma_disconnect(conn_id);
    rdma_destroy_ep(conn_id);
    rdma_destroy_ep(listen_id);
    ```
  </Tab>
  <Tab title="Client (active side)">
    The client resolves the server address and creates a connected endpoint using `rdma_create_ep`, then calls `rdma_connect`.

    ```c
    #include <rdma/rdma_cma.h>

    struct rdma_addrinfo hints = {
        .ai_port_space = RDMA_PS_TCP,
    };
    struct rdma_addrinfo *res;
    struct rdma_cm_id *id;
    struct ibv_qp_init_attr qp_init_attr = {
        .cap = {
            .max_send_wr  = 64,
            .max_recv_wr  = 64,
            .max_send_sge = 1,
            .max_recv_sge = 1,
        },
        .qp_type = IBV_QPT_RC,
    };

    /* Resolve server address */
    rdma_getaddrinfo("192.168.1.10", "7471", &hints, &res);

    /* Create endpoint with a QP */
    rdma_create_ep(&id, res, NULL, &qp_init_attr);
    rdma_freeaddrinfo(res);

    /* Connect to the server */
    rdma_connect(id, NULL);

    /*
     * The QP (id->qp) is now ready.
     * Post receives and sends, then disconnect.
     */
    rdma_disconnect(id);
    rdma_destroy_ep(id);
    ```
  </Tab>
  <Tab title="Asynchronous event loop">
    For full asynchronous control, create an event channel explicitly and use `rdma_get_cm_event` to drive state transitions.

    ```c
    #include <rdma/rdma_cma.h>

    struct rdma_event_channel *ec;
    struct rdma_cm_id *id;
    struct rdma_cm_event *event;

    ec = rdma_create_event_channel();
    rdma_create_id(ec, &id, NULL, RDMA_PS_TCP);

    /* Resolve address (asynchronous) */
    struct sockaddr_in dst = {
        .sin_family = AF_INET,
        .sin_port   = htons(7471),
    };
    inet_pton(AF_INET, "192.168.1.10", &dst.sin_addr);
    rdma_resolve_addr(id, NULL, (struct sockaddr *)&dst, 2000 /*ms*/);

    while (rdma_get_cm_event(ec, &event) == 0) {
        switch (event->event) {
        case RDMA_CM_EVENT_ADDR_RESOLVED:
            rdma_ack_cm_event(event);
            rdma_resolve_route(id, 2000);
            break;
        case RDMA_CM_EVENT_ROUTE_RESOLVED:
            rdma_ack_cm_event(event);
            rdma_connect(id, NULL);
            break;
        case RDMA_CM_EVENT_ESTABLISHED:
            rdma_ack_cm_event(event);
            /* Connection ready — begin data transfers */
            goto done;
        default:
            rdma_ack_cm_event(event);
            break;
        }
    }
done:
    /* ... data path ... */
    rdma_disconnect(id);
    rdma_destroy_id(id);
    rdma_destroy_event_channel(ec);
    ```
  </Tab>
</Tabs>

## Connection events

The `rdma_cm_event_type` enum defines all events that can be delivered on an event channel:

| Event | Description |
|---|---|
| `RDMA_CM_EVENT_ADDR_RESOLVED` | Address resolution completed successfully. |
| `RDMA_CM_EVENT_ROUTE_RESOLVED` | Route resolution completed successfully. |
| `RDMA_CM_EVENT_CONNECT_REQUEST` | Incoming connection request (server side). |
| `RDMA_CM_EVENT_ESTABLISHED` | Connection established. |
| `RDMA_CM_EVENT_DISCONNECTED` | Connection disconnected. |
| `RDMA_CM_EVENT_DEVICE_REMOVAL` | RDMA device was removed; destroy all associated resources. |
| `RDMA_CM_EVENT_ADDR_ERROR` | Address resolution failed. |
| `RDMA_CM_EVENT_ROUTE_ERROR` | Route resolution failed. |
| `RDMA_CM_EVENT_REJECTED` | Connection request was rejected by the remote side. |

Use `rdma_event_str(event->event)` to convert an event type to a human-readable string.

## rsocket

librdmacm includes `rsocket`, a socket-compatible RDMA interface. Existing socket-based applications can be run over RDMA without source changes by preloading the `librspreload` library:

```bash
LD_PRELOAD=/usr/lib/rsocket/librspreload.so ./your_socket_app
```

The `rs_*` functions (`rsocket`, `rbind`, `rconnect`, `rlisten`, `raccept`, `rsend`, `rrecv`, and so on) mirror the POSIX socket API and can also be called directly from applications that want explicit control over RDMA socket semantics.

<Note>
rsocket performance depends on the application's I/O pattern. Applications that transfer large buffers in few operations benefit the most. Applications that issue many small transfers with high call frequency may see less improvement.
</Note>
